### 8B-02 — P2: Local HTTP, errors and idempotency remain an outline

**Triage: decision**

**Owner:** [Architecture](intent://local/upon-build/note/c0689bcd-8dca-4ce6-bccb-e538e0a45477) §§5.2/7.2/8, `architecture.md:327–360,446–458,478–489`; [Testing](intent://local/upon-build/note/d7819c6b-68ff-4d89-835d-9acabe779cae) §§5/7, `testing.md:154,220–224`.

**Evidence / impact:** Routes and durable dedup are present. Missing wire schemas/status mapping include bootstrap/session/CSRF exchange, 202 preparation status versus accepted/rejected Receipt, unknown receipt, same-ID/different-body conflict, staging offsets/resume/finalize, stream cursor/gap envelopes and content-range failures. The Receipt union lists five domain codes, while §8 names additional credential/storage/protocol cases without identifying which are HTTP failures, durable rejections or job states. “Canonical-body-hash” has no canonicalization contract. Independent frontend/backend implementations must invent matching choices.

**Proposed fix:** One versioned local protocol appendix/schema with example request/response/error bodies, auth/CSRF requirements, status codes, command hashing inputs/normalization, pending-operation identity, upload ownership/resume/finalize semantics and event transaction/cursor rules. Distinguish retry-safe local delivery, retryable reads/transfers and uncertain paid dispatch. Keep all mutations through existing actions.

**User decision:** Required under the current triage policy: request/response schemas, status mappings, command hashing and upload/stream semantics add or choose contract behavior. They can preserve accepted product choices, but are not editorial.
**Re-verify:** Table every listed route against schemas/examples and error/retry behavior; later real HTTP integration cases for duplicate delivery, changed-body ID, stale revision, pending→receipt, reconnect gaps and resumed upload.

### 8B-03 — P2: Localhost threat model needs concrete acceptance rules

**Triage: decision**

**Owner:** [Architecture](intent://local/upon-build/note/c0689bcd-8dca-4ce6-bccb-e538e0a45477) §8, `architecture.md:491–497`; [Testing](intent://local/upon-build/note/d7819c6b-68ff-4d89-835d-9acabe779cae) §7, `testing.md:224`; Index Q26.

**Evidence / impact:** Loopback binding, Host/Origin checks, pairing cookie and mutation CSRF are already required. There is no explicit attacker/trust-boundary table or exact policy for bootstrap delivery/reuse/expiry, host+port/IPv6 aliases, absent or null Origin, allowed dev proxy headers, session renewal/revocation, or sensitive GET/stream access. DNS rebinding is not named; merely saying “reject unexpected Host/Origin” leaves its test oracle unspecified.

**Proposed fix:** Specify launch/bootstrap trust and exact accepted origins/hosts, authenticate sensitive reads as well as writes, define absent-Origin behavior by request class, and add negative browser/HTTP cases for hostile sites, rebinding Host values, spoofed forwarded headers, reused pairing tokens and expired sessions. State that a compromised same-OS-user process is outside the pairing defense; define storage-root permissions. Add a bounded browser-content policy for untrusted text/downloads rather than treating loopback as trusted content.

**User decision:** Required under the current triage policy: exact bootstrap/session/origin/content-access rules choose security contract behavior, even while preserving the single-user localhost model. Remote access or a changed trust model also requires a decision.
**Re-verify:** Review a threat→control→test matrix; later L/B tests must reject hostile requests with zero state/provider effects. OWASP's [CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) supports exact origin handling; the finding is about missing app-specific rules, not a proven exploit.

### 8B-04 — P2: Result fetching lacks a sealed egress and credential policy

**Triage: decision**

**Owner:** [Architecture](intent://local/upon-build/note/c0689bcd-8dca-4ce6-bccb-e538e0a45477) §§7.2/8, `architecture.md:458,493–497`; [API](intent://local/upon-build/note/2728dafd-4209-4558-a762-3a0192e0610f), Transport, `api.md:160–168`; [Testing](intent://local/upon-build/note/d7819c6b-68ff-4d89-835d-9acabe779cae), `testing.md:66,154`.

**Evidence / impact:** HTTPS/host/redirect/resolved-address validation and private-address rejection are present. Missing are the approved host/port classes, which calls receive FAL_KEY, redirect credential stripping, connection-time DNS/address policy, byte/time limits, and the test-only exception for the localhost provider emulator. A hostname allowlist alone does not define these behaviors.

**Proposed fix:** Separate authenticated queue transport from credential-free asset fetching, use a versioned allowlist, explicitly reject or validate each redirect, bind address validation to the actual connection and cover IPv4/IPv6 representations. Deny ambient proxy/credential inheritance unless explicitly configured. Keep emulator exceptions test-only and production-inaccessible. Reuse existing transfer/admission budgets.

**User decision:** Required under the current triage policy: host/credential/redirect/DNS and connection policies choose transport behavior. Keep arbitrary URL imports deferred.
**Re-verify:** Future fixtures for allowed host→private redirect, changed DNS answer, mixed address families, oversized/no-length response, credential sentinel on asset host and rejected production emulator override. These are applications of [OWASP SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html), not live attack tests.

### 8B-05 — P2: Portable format and hostile-upload validation need a concrete profile

**Triage: decision**

**Owner:** [Architecture](intent://local/upon-build/note/c0689bcd-8dca-4ce6-bccb-e538e0a45477) §§8/9.3/16.7, `architecture.md:486–488,497,543–547,944–950`; [Testing](intent://local/upon-build/note/d7819c6b-68ff-4d89-835d-9acabe779cae), `testing.md:222–224`; Index Q18/Q27.

**Evidence / impact:** Closure, safe paths, hashes, bounded parsing and atomic publication are present. The archive is still a proposal: no normative container/manifest/entry/event encoding profile or exact validation order. “Compression ratio/total bytes” and “bounded” leave archive bombs, duplicate/colliding entries, symlink/hardlink/device entries and partial-import cleanup without a shared oracle. A generic fixed 4GiB cap would contradict the existing larger-copy policy.

**Proposed fix:** Define a versioned portable-format manifest and import algorithm before writer/export implementations diverge. If ZIP is chosen, specify large-file support. Validate entries into isolated staging, reject unsafe names/types/collisions, stream hashes and decompression within resource reservations, then publish once. Define route/type-specific upload/parser limits using existing envelopes; preserve original files and distinguish failed staging from owned assets.

**User decision:** Required under the current triage policy: portable encoding and validation profiles choose contract behavior. New hard limits or restrictions affecting accepted full-history/large-copy behavior must be explicitly identified.
**Re-verify:** Static schema/sample archive walkthrough; later real-file integration cases for traversal, duplicate names, expansion bomb, interrupted import, oversized image decode, hash mismatch and >4GiB streamed closure. [OWASP upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) supports validation beyond MIME and decompressed-size control.

### 8B-06 — P2: Remote privacy defaults have evidence but no selected app policy

**Owner:** [API](intent://local/upon-build/note/2728dafd-4209-4558-a762-3a0192e0610f), retention/uploads, `api.md:188–194`; [UX](intent://local/upon-build/note/3febb57d-ea57-42de-a098-b12fb4e010e4) §6 transport, `ux.md:359`; [Architecture](intent://local/upon-build/note/c0689bcd-8dca-4ce6-bccb-e538e0a45477) §8, `architecture.md:495`; Index Q09.

**Evidence / impact:** API evidence distinguishes payload history, CDN ACL/lifetime and local storage. **Proposed fix:** Add a data-egress/retention table: prompt, source/mask, adapters, training archive, outputs; destination, metadata sent, remote policy/default, uncertainty and deletion limits. Recommend minimum provider persistence and private access compatible with documented deferred fetch, with explicit fallback disclosure when that cannot be guaranteed. **User decision:** Required: select new remote privacy/retention defaults after checking provider feasibility. Preserve U09 local retention and full-history copies. This audit selects no TTL or policy.
**Re-verify:** Chosen values must exist in the owning clauses and request fixtures, with expiry/offline/recovery cases. External evidence freshness remains Task 8C's responsibility.

### 8B-07 — P2: Exact transport provenance and portable secret exclusion need a typed boundary

**Triage: decision**

**Owner:** [Architecture](intent://local/upon-build/note/c0689bcd-8dca-4ce6-bccb-e538e0a45477) §§9.3/16.7, `architecture.md:543–547,942–946`; [Performance](intent://local/upon-build/note/1b7b659d-d577-4257-b677-4850bbf86143) §7 receipt privacy, `performance.md:673–677`; [Testing](intent://local/upon-build/note/d7819c6b-68ff-4d89-835d-9acabe779cae), `testing.md:224`.

**Evidence / impact:** §16.7 says retain exact response bytes as transport provenance. Responses can include signed result URLs; copies exclude signed transport URLs, and PERF diagnostics are protected/redacted. Full closure retains job/raw provenance, but no type/closure rule explicitly separates the exact transport blob from portable safe provenance. The intended rules can coexist, but copying every provenance reference or redacting the only “exact” blob would violate one of them.

**Proposed fix:** Distinct backend-only transport evidence and portable sanitized response records; explicit export exclusion and retention/access rules for the former. Preserve exact requested/submitted/returned prompt bytes as the separately owned caption records already specified. Redaction produces a derived record, never falsely relabels bytes as exact.

**User decision:** Required under the current triage policy: typed record/export/retention boundaries complete contract behavior. Preserve accepted secret exclusion and exact prompt provenance; their existing wording alone does not pre-approve this specific implementation contract.
**Re-verify:** Fixture containing signed URL, cookie/key/error sentinel and escaped/oversized prompt: local record classes correct, portable archive contains no transport secret, prompt bytes remain exact, reopen makes zero remote calls.

### 8B-08 — P2: Whole-document deletion is promised but root-release semantics are incomplete

**Triage: decision**

**Owner:** [UX](intent://local/upon-build/note/3febb57d-ea57-42de-a098-b12fb4e010e4) §5, `ux.md:266–270`; [Architecture](intent://local/upon-build/note/c0689bcd-8dca-4ce6-bccb-e538e0a45477) §§5.1/9.2, `architecture.md:321–323,523–533`.

**Evidence / impact:** Retention/GC is substantial, and UX explicitly permits backing up and deleting a whole document. But the deletion transaction does not say which document/history/checkpoint/draft/job roots are removed, which shared assets remain, how active/uncertain jobs and late results behave, or when quarantine/staging/backups remain after deletion. Candidate tombstones alone cannot free bytes still rooted by job provenance. This is not a request for the deferred history-prune UI.

**Proposed fix:** A dependency-aware whole-document deletion/root-release table, preview, durable receipt and restart/race rules. Clearly state local physical deletion versus retained shared roots, grace/quarantine, external bundles/backups and provider copies. Keep default indefinite candidates/full history until an explicit eligible deletion.

**User decision:** Required under the current triage policy: root-release, active-job/late-result and deletion-recovery rules complete behavior. The existing whole-document deletion promise is preserved; automatic expiry, pruning or shared-data erasure is not approved.
**Re-verify:** Future L/B cases: sole-root document, shared asset, retained checkpoint, running/uncertain job, late completion and restart during GC; no collateral deletion and honest bytes-freed status.
