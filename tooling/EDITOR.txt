Additive read adapters (coordinator-authorized in task292d3ac5 / shared PR Context):
GET /api/v1/commands/:id/result returns the existing CommandResult for pending,
unknown or rejected work. An accepted command gets one complete EventPage over
its immutable receipt's exact from/to/transaction range, even when ordinary
recovery now requires a newer snapshot. Existing bounded inline/reference
encoding and current-session, writer-epoch read leases apply. This is result
inspection, never publication of a domain recovery cursor or renewed review.
GET /api/v1/commands/:id/original returns the exact validated original UTF-8
request bytes, only to the currently authenticated original client. Pending to
terminal movement does not change this identity. Unknown remains unknown.
GET /api/v1/commands/pending?cursor= lists only that client's currently pending
journals. Pages contain at most32 metadata records and stay below64KiB.
GET /api/v1/ui?cursor= lists at most64 current owned UI checkpoint metadata rows
(sessionId, documentId, uiSeq), with selected content read using existing GET.
Both inventories use opaque current-owner/session/epoch-scoped keyset cursors,
a fixed initial upper key, and30-minute/session-bounded read lifetimes. They
are live at each page read, not frozen membership snapshots: completion before
visiting a pending row removes it from that page; later admission may require
a fresh listing. Listed pending IDs remain lookupable through terminal races.
UI changes are checked again against selected sessionId/uiSeq before restoration;
sequences from different UI sessions never establish cross-session ordering.
No total-count cap, schema change, history pruning or domain cursor publication.
Queries use existing tables, so repeated JSON ownership scans are not a100k
operation qualification. Existing bounded read-context limits still apply.

Each browser tab owns a logical UI session, retained in sessionStorage for its
reload. It is data identity, not authentication. New-origin restart discovers
owned checkpoints; the user explicitly chooses the view/drafts to restore.
No automatic choice among several saved sessions, no resurrection of applied
or cleared drafts. Commands keep original owner/session/correlation/transaction
identities. The disposable browser delivery journal never stores cookies,
pairing tokens or CSRF. Unuploaded bytes and unknown requests lost with the
origin cannot be invented; transfer recovery asks for the exact original file.

Verification and known limits are recorded in the task and final evidence
manifest. Browser automation does not qualify native OS pickers, IME/AT,
power-loss, large-envelope or formal platform/performance campaigns. The
existing A-R01 and historical timing failures remain open and disclosed.

Additive document revision probe (explicit P1b.7 extension, not baseline behavior):
HEAD /api/v1/documents/:id uses the same current authentication/root boundary as
GET and returns X-App-Entity-Version as the canonical decimal revision string.
It has no body, projection serialization, content registration or read lease.
Unknown, expired, foreign-origin, query and method errors preserve the existing
boundary without disclosing a revision. It is mutable metadata, never a token.
The browser binds this final equality check to its selected document, connection
lifetime and recovered cache generation. Image content hash plus the monotonic
document revision cover its image/history/checkpoint domain transactions; UI
checkpoints remain independently fenced by sessionId/uiSeq/generation. This is
not an atomic snapshot API and does not advance the recovery cursor.
